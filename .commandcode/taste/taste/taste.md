# Taste
- Prefers very concise answers — explicitly asks to "answer in one line" and expects responses condensed to a single line when requested. Confidence: 0.7
- Specifies requirements as explicit numbered rule lists that enumerate the expected behavior for each edge case (e.g. create vs update vs stock paths) and expects them implemented literally, letting code follow the stated rules rather than the assistant substituting its own judgment. Confidence: 0.5
- Wants a markdown handoff/context doc at the repo root (e.g. `PROJECT_CONTEXT.md`) capturing architecture, environment variable names, code map, setup commands, current status, caveats, and next steps — so work can be resumed from a different machine — and expects it maintained idempotently: create it if missing, update it in place if it already exists rather than making a new file. Confidence: 0.7
- Wants the assistant to proactively locate and read a project's markdown docs (README, AGENTS.md, CLAUDE.md, PROJECT_CONTEXT.md, etc.) to understand the project before doing work, and expects a summarizing read-back of that context. Confidence: 0.6
- Pasting raw terminal/error output or full runtime log dumps (including full HTML error bodies, stack traces, and dev-server logs) with no or minimal accompanying question, and expecting the assistant to review the trace and identify the root cause and the concrete fix — often without any ask. Confidence: 0.6
- Expects sync/replication to cover every matching target rather than just the first/default one — e.g. a quantity change should update the destination's *all* locations, not a single primary. Confidence: 0.5
- Expects record matching to be sym/identity-driven and consistent across event types: a webhook update should behave like a create — create the destination record when its identity key (e.g. SKU) is absent and update it when present, and only skip when the source has no identity key at all; rejects special-casing "update mode never creates". Confidence: 0.6
- Explicitly wants code that is readable and easy to understand, avoiding unnecessary complexity. Confidence: 0.8
- Expects a record created/synced in the destination to be a faithful mirror of the source, wanting maximum completeness: explicitly asks to copy "all, byte for byte" (full field parity) rather than a minimal/core-fields subset, and is willing to accept the extra source reads and destination mutations that full-field copying requires. Reports incomplete destination copies as bugs, describing the visible symptom in the destination admin (e.g. a variant showing "Inventory not tracked" or the product image missing after a save). Confidence: 0.75
- Wants logging/instrumentation added so they can track runtime behavior — asks for logs to follow what happens, favoring a single consistent, greppable log line per event (e.g. a scope-prefixed `key=value` format) over ad-hoc `console` calls scattered around. Confidence: 0.6
- Wants end-to-end visibility into *where a request currently is* — instrumentation covering every stage: inbound webhook receive/send, what data was read (payload/source), the main processing/decision steps, each outbound API call's send *and* receive (with a labeled operation and timing), and completion — so the current phase can be inferred from the last log line. Confidence: 0.6
- Expects the assistant to read the whole codebase first, then proactively find and simplify overly complex design/code (behavior-preserving) rather than only doing the literal ask. Confidence: 0.5
- Prefers minimal, necessary-only code: questions whether a proposed change (e.g. a defense-in-depth source guard) is actually required before accepting it, declines optional code when existing behavior already works, and proactively asks to audit and strip unused/dead code (unused re-exports, unused fields, and `export` on internal-only symbols). Confidence: 0.6
- Distrusts assertions and demands verification against the real code rather than a restated claim: challenges the provenance of any value the assistant relies on (e.g. "how are you getting that quantity is being updated?") and questions whether claimed work was actually done (e.g. "do you added requred logs?"), expecting a concrete trace through the code (grep/read reaching every call site) plus docs — and expects the assistant to close any gaps it finds. Will correct the assistant when the assumed data source doesn't match their observed workflow. Confidence: 0.6
